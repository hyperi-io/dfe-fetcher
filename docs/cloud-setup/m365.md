# M365 Setup for dfe-fetcher

What a cloud administrator configures so dfe-fetcher can read security and
audit data from Microsoft 365 (read-only, pull-mode).

## Overview

dfe-fetcher reads M365 over two parallel surfaces, authenticating to each via
the OAuth2 client_credentials flow against
`https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`:

- **Office 365 Management Activity API** (`manage.office.com`, scope
  `https://manage.office.com/.default`) - raw per-event audit records, fetched
  per content type. Backs `audit_log`, `dlp`, and `exchange_audit`.
- **Microsoft Graph Security** (`graph.microsoft.com`, scope
  `https://graph.microsoft.com/.default`) - curated, post-classification
  alerts from `security/alerts_v2`. Backs `alerts` only.

Services and their behaviour:

| Service | Surface | What it pulls |
|---------|---------|---------------|
| `audit_log` | OMAP | Iterates content types. Default set: `Audit.General`, `Audit.AzureActiveDirectory`, `Audit.Exchange`, `Audit.SharePoint`, `DLP.All`. Emits one result per content type, tagged `m365.audit_log.<content_type>`. Override with service config `content_types: [...]`. |
| `exchange_audit` | OMAP | `Audit.Exchange` only - per-message audit records. Tagged `m365.exchange_audit`. |
| `dlp` | OMAP | `DLP.All` only - raw DLP rule-match events. Tagged `m365.dlp`. |
| `alerts` | Graph | `GET /v1.0/security/alerts_v2`. Tagged `m365.alerts`. |

The OMAP path enables (or re-arms) the subscription for each content type
automatically before fetching, splits windows into <=24h chunks, follows
`NextPageUri` pagination, then downloads each content blob. A one-time manual
subscription start is still the recommended bootstrap (see Source-Side Setup).

## Prerequisites

- An Entra ID (Azure AD) tenant with M365 audit logging enabled in the Purview
  / compliance portal (the unified audit log must be turned on for OMAP to
  return content).
- An Entra app registration (`client_id`) with a client secret, in the target
  tenant (`tenant_id`).
- A Global Administrator (or Application Administrator) to grant admin consent.
- `az` CLI logged into the target tenant, or Terraform with `az login`.

## Required Permissions

All permissions are **application** (app-only, not delegated) and **read-only**.
Resource App IDs: Office 365 Management API = `c5393580-f805-4401-95e8-94b7a6ef2fc2`,
Microsoft Graph = `00000003-0000-0000-c000-000000000000`.

| Used by | API | Permission | Permission ID | Type |
|---------|-----|------------|---------------|------|
| `audit_log`, `exchange_audit` | Office 365 Management | `ActivityFeed.Read` | `594c1fb6-4f81-4475-ae41-0c394909246c` | Application |
| `dlp` | Office 365 Management | `ActivityFeed.ReadDlp` | `4807a72c-ad38-4250-94c9-4eabfe26cd55` | Application |
| `alerts` | Microsoft Graph | `SecurityAlert.Read.All` | `472e4a4d-bb4a-4026-98d1-0b0d74cb74a5` | Application |

**Notes:**

- `ActivityFeed.Read` covers the `Audit.*` content types. `DLP.All` content
  (sensitive-data detections) requires `ActivityFeed.ReadDlp`. Grant both if you
  fetch `dlp` or the default `audit_log` set (which includes `DLP.All`).
- `472e4a4d-bb4a-4026-98d1-0b0d74cb74a5` is the **application** ID for
  `SecurityAlert.Read.All` (the delegated variant is a different GUID). This is
  the only Graph permission the current code needs - it reads `alerts_v2`.
  `SecurityEvents.Read.All` (the legacy `alerts_v1` permission) and
  `Reports.Read.All` are provisioned by the test Terraform for convenience but
  are not required by the live code path.

## Source-Side Setup

### Terraform (Automated)

The test infrastructure lives in
[`infra/test/main.tf`](../../infra/test/main.tf) (M365 section). It creates an
app registration with the permission IDs above, a service principal, and a
client secret.

```bash
cd infra/test
cp terraform.tfvars.example terraform.tfvars
az login   # must target the M365 tenant
terraform init
terraform apply
terraform output -json | python3 gen-env.py > ../../.env
```

Terraform cannot grant admin consent. After apply (requires Global Admin):

```bash
az ad app permission admin-consent --id <m365_client_id>
```

### Manual Setup (az CLI)

1. **Create the app registration**

   ```bash
   az ad app create --display-name "dfe-fetcher-m365"
   ```

2. **Add the Office 365 Management API permissions**

   ```bash
   # ActivityFeed.Read
   az ad app permission add --id <app_id> \
     --api c5393580-f805-4401-95e8-94b7a6ef2fc2 \
     --api-permissions 594c1fb6-4f81-4475-ae41-0c394909246c=Role
   # ActivityFeed.ReadDlp (for the dlp service / DLP.All content)
   az ad app permission add --id <app_id> \
     --api c5393580-f805-4401-95e8-94b7a6ef2fc2 \
     --api-permissions 4807a72c-ad38-4250-94c9-4eabfe26cd55=Role
   ```

3. **Add the Microsoft Graph permission**

   ```bash
   az ad app permission add --id <app_id> \
     --api 00000003-0000-0000-c000-000000000000 \
     --api-permissions 472e4a4d-bb4a-4026-98d1-0b0d74cb74a5=Role
   ```

4. **Grant admin consent** (Global Admin)

   ```bash
   az ad app permission admin-consent --id <app_id>
   ```

5. **Create a client secret**

   ```bash
   az ad app credential reset --id <app_id> --years 1
   ```

6. **Create the service principal** (if not auto-created)

   ```bash
   az ad sp create --id <app_id>
   ```

7. **Activate the OMAP audit subscriptions.** The Office 365 Management
   Activity API will not return content until a subscription is started per
   content type. dfe-fetcher re-arms subscriptions automatically, but do this
   once to bootstrap so the very first fetch has data:

   ```bash
   TENANT_ID="your-tenant-uuid"
   TOKEN=$(az account get-access-token \
     --resource https://manage.office.com --query accessToken -o tsv)

   for CT in Audit.General Audit.AzureActiveDirectory Audit.Exchange Audit.SharePoint DLP.All; do
     curl -s -X POST \
       "https://manage.office.com/api/v1.0/${TENANT_ID}/activity/feed/subscriptions/start?contentType=${CT}" \
       -H "Authorization: Bearer ${TOKEN}" -H "Content-Type: application/json" -d '{}'
   done
   ```

   Subscriptions persist until explicitly stopped. Verify consent later with:

   ```bash
   az ad app permission list-grants --id <app_id>
   ```

## dfe-fetcher Configuration

### Config File

```yaml
sources:
  m365:
    enabled: true
    tenant_id: "your-tenant-uuid"
    client_id: "your-client-uuid"
    client_secret: "your-client-secret"
    services:
      - name: audit_log
        # config:
        #   content_types: ["Audit.General", "Audit.SharePoint"]  # opt out of feeds
      - name: exchange_audit
      - name: dlp
      - name: alerts
    topic: "m365"
    # filter: 'Workload != "Exchange"'   # CEL, hot-reloaded
```

Recognised top-level fields: `enabled`, `tenant_id`, `client_id`,
`client_secret`, `credential_secret`, `interval_secs`, `services`, `topic`,
`filter`, `management_url_override`, `graph_url_override`,
`token_url_override`. There is no `message_trace` service - the OMAP
`Audit.Exchange` feed is `exchange_audit`. Use `exchange_audit`; the legacy
name `message_trace` is not dispatched by the current module and is skipped
with an "Unknown M365 service" warning.

An optional `M365_PUBLISHER_IDENTIFIER` environment variable sets the OMAP
`PublisherIdentifier` (per-publisher rate-limit budget). Set it per deployment
so tenants do not share a budget.

### Environment Variables

Pattern: `DFE_FETCHER_SOURCES__M365__<FIELD>` (double underscores).

```bash
DFE_FETCHER_SOURCES__M365__ENABLED="true"
DFE_FETCHER_SOURCES__M365__TENANT_ID="your-tenant-uuid"
DFE_FETCHER_SOURCES__M365__CLIENT_ID="your-client-uuid"
DFE_FETCHER_SOURCES__M365__CLIENT_SECRET="your-client-secret"
```

### Secrets Manager

Set `credential_secret` to a secret-store spec. NOTE: in the current code,
`credential_secret` resolves to a single string used for BOTH `client_id` and
`client_secret`, so store the value the token endpoint expects (typically the
client secret) and supply `client_id` separately, or keep both in plain config.
Do not assume a JSON blob is parsed.

```yaml
sources:
  m365:
    enabled: true
    tenant_id: "your-tenant-uuid"
    client_id: "your-client-uuid"
    credential_secret: "vault:secret/dfe/m365:client_secret"
    services:
      - name: audit_log
      - name: alerts
    topic: "m365"
```

For multiple tenants (MSP scenario), run one dfe-fetcher instance per tenant -
each with its own app registration, admin consent, activated subscriptions, and
a distinct `instance_id`.

## Verification

1. **Health check.** `M365Source::health_check` acquires the **management**
   token only. A healthy result confirms OMAP-backed services will authenticate;
   Graph `alerts` needs the separate `SecurityAlert.Read.All` grant, which the
   health check does not exercise.

2. **Env-gated smoke tests.** Live tests live in
   [`tests/e2e/smoke_remote.rs`](../../tests/e2e/smoke_remote.rs), all
   `#[ignore]`'d. M365 tests reuse the Azure SP env vars - `AZURE_TENANT_ID`,
   `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` (M365 is Entra-fronted, so no
   separate `M365_*` vars).

   ```bash
   cargo test --test e2e m365_ -- --ignored --nocapture
   ```

   Configure the `exchange_audit` service directly; `message_trace` is not a
   valid service name.

3. **Common failures.**
   - `403 Forbidden` on every call: admin consent not granted.
   - `403` on `alerts` only: missing `SecurityAlert.Read.All`.
   - `audit_log`/`dlp` returns nothing: unified audit log not enabled in
     Purview, or subscription never started (the bootstrap step). dfe-fetcher
     auto re-arms on a `404` content-list response.
   - DLP content missing while `Audit.*` works: missing
     `ActivityFeed.ReadDlp`.
   - HTTP 429: OMAP throttling - dfe-fetcher backs off 30s and retries; set a
     unique `M365_PUBLISHER_IDENTIFIER`.

## Cost

dfe-fetcher only reads. Entra ID app registrations, Office 365 Management
Activity API reads, and Microsoft Graph Security API reads are not expected
to carry an additional charge, though this can depend on your M365 licensing.
Confirm any cost implications against your own Microsoft agreement.
